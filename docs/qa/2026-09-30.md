## Bugs found and fixed (branch commits)

1. **Keeper `numRequiredSignatures` (dry-run error)**: root cause is two installs of `@solana/web3.js` (pnpm peer-dependency variants: `utf-8-validate@5` and `@6`). The keeper built a legacy `Transaction`, the app's `Connection` (`SplitConnection`) is from the other copy, `instanceof Transaction` failed and web3.js tried to populate it as a Message. It broke every keeper simulation: `apply_yield`, `send_pay_yield`/`send_unlock` fee quotes, and the Hold'em `claim_timeout` / `close_match` and Block Puzzle `seal` free checks. `keeper/src/tee.ts` now simulates a `VersionedTransaction` (matched by shape). Dry run now says `would apply_yield` / `would send_pay_yield`, and both were then sent for real.
2. **Keeper loop died on a dropped connection** (`fetch failed` before the first job): a failed pass is now logged and retried.
3. **Hold'em Queue never paired**: `findQueueMatch` required a Block Puzzle Session on the opener, which Hold'em tables do not have, so two Hold'em Players each opened their own Match and both waited (`app/src/lib/chain/read.ts`).
4. **Sweep surplus always failed** (`ConstraintMut`): after F-05 the program mutates `custody.tracked_shares` but the client (`app/src/lib/chain/native.ts`, `scripts/native-position`) still passed the custody read-only. Added an IDL test (`native.test.ts`) that checks every native instruction's writable/signer flags against the IDL.
5. **Client Debt projection ignored `tracked_shares`**: it used the vault's token balance, so a direct top-up showed as repaid Debt ("Unlock" looked available) while the program (correctly, F-05) ignored it. `fetchNativeInfo` now reads `tracked_shares`.
6. **Stale copy**: "Take a demo Advance in your Wallet" (the demo Advance is off) became "Open a Position in your Wallet"; the "more than two Sources" hint no longer says "play a smaller entry" (500 is the minimum) but "Redeem a few small balances".
7. **Public devnet RPC 429s** ("Rate limited upstream" on Backing while posting a Request, with three browsers and the keeper): the default `getProgramAccounts` RPC is now `https://rpc.magicblock.app/devnet` (verified: serves gPA); `app/docs/rpc.md` updated. Set `TESORO_GPA_RPC` / `KEEPER_GPA_RPC` to override.

## Program bugs for the orchestrator (nothing deployed)

None confirmed. Two design points worth a decision, not defects:

- **Entry fragmentation dead end.** `planEntry` follows tesoro_core's canonical drain order (own class first, ascending Source key, at most two Sources per entry). An Account whose Gemas are spread over three or more Sources (two own Positions plus Gemas won from others) cannot enter a 500 Match even with 1,291 Gemas (`qa2`); the message told the user to "play a smaller entry first", which is impossible (500 is the minimum). Reproduce: two native Positions, win a Match against two different opponents, try `/play/queue?entry=500`. Workaround: Redeem the small balances so fewer Sources remain. A program change (allow the client to skip empty or tiny Holdings, or raise the cap) would remove it.
- **Failed `finalize` retries.** Both Hold'em clients call `finalize` in a loop; the loser of the race gets `Custom 6018` and each failed try costs a base fee (five failed txs beside the one that landed on Match `3581505881060`). Harmless but noisy; a "settled?" read before sending would avoid it (app side).

## Known limitations

- Reloading during a Block Puzzle run ends the run with the score so far (the Seed is hidden in the rollup; the client cannot rebuild the board). By design (`MatchView`: "the run cannot be resumed, so close it with what landed").
- Hold'em table setup takes about 2 minutes (create, delegate, permissions, VRF, deal). The Claim timeout path needs the 30 s clock plus one or more presses; the TEE transactions are private, so there are no signatures to link for them.
- The Backing, Lobby and Play lists are `getProgramAccounts` reads cached in the app server (4 s fresh, 2 min stale-while-revalidate): a cancelled Request or new Offer can take up to a couple of minutes to show on another Account's screen.
- Unlock returns the Principal minus the yield still owed to outstanding Gemas of that Source (holders who won them can still redeem); Sweep collects what is left later.
- The browser console shows `signatureSubscribe` JSON-RPC errors (about 2 per second while a Hold'em table is open): the confirmation WebSocket is refused by the endpoint, polling takes over. Cosmetic.
- The keeper still reports yield for test Positions on the RETIRED Hoodi vault `0x8289...` (they have Debt), spending a little ETH each 10 minutes.
- Positions on the retired vaults and the old `1790715823104` Hold'em table, `3581435845959` / `3581442765258` / `3581442404416` Block Puzzle Matches are left as they were (the keeper waits for their deadline paths).
- `qa1`..`qa5` are dev-wallet Accounts (keys in the browser localStorage of the QA harness only); their Matches and Positions remain on devnet.
- HyperEVM: no vault deployed (no HYPE), not tested.
