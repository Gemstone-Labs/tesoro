## Bugs found

Fixed on `qa/app-live-pass-01-10-2026` (one-line label fix, the only code change):

5. **The Backer's backed-loss split said "Your Player bears the loss".** On a backed loss the Backer's result read "Your Player bears the loss −500 / Player owes 0 Gemas · 0 Debt", which contradicts itself and CONTEXT.md (only the Backer bears a loss). `app/src/components/match/BackingSplit.tsx:54` now reads "You bear the loss" in the Backer's view (the Player's view still says "Your Backer bears the loss"). Commit `7b6c36a`; verified live on Match `3581736635696` (screen `j5-result-backer-lost-fixed`); tsc, eslint, vitest 212/212 pass.

Not fixed (QA only):

1. **P1: a holder who never opened an ETH Position cannot redeem ETH-Sourced Gemas, and the failure is silent.** Repro: Account B wins Gemas from an ETH Source (any Match against A while A holds ETH-Sourced Gemas), never opens an ETH Position, opens Wallet → Redeem → "Redeem N". The native rows redeem; `redeem_to_evm` fails `Custom 6019` NoEvmAddress (`bridge/programs/tesoro_bridge/src/errors.rs:24`); the sheet closes about 2 s later with no error, no tracker, and the ETH rows stay redeemable. Cause: `redeemEthSource` (`app/src/app/wallet/EthPositions.tsx:623–633`) never calls `ensureEvmLinked` (`app/src/lib/chain/eth-flow.ts:90`), which only the open flow calls (`eth-flow.ts:163`). Also `RedeemForm` silently skips ETH rows when `useEthCtx()` is null (`app/src/app/wallet/NativePositions.tsx:315`, `if (ethRows.length > 0 && ethCtx)`). Every winner of ETH-Sourced Gemas hits this unless they hold an ETH Position. Workaround: open any ETH Position first.
2. **P1 for the demo: simulated yield runs ~2.5x slower than the Horizon, and the gap grows by ~0.83x per real day.** The sim_lst rate is simple interest on a fixed base (`rate = base·(1 + apy·t·speedup/YEAR)`, `app/src/lib/chain/native.ts:229`, same as the program): base 1.0 at 2026-09-29 21:41, 700 bps, speedup 4,320, rate now 2.47. The Advance is quoted on the current value (`quoteNativeAdvance`, `native.ts:238`, mirrors `Position::open_advance`), but the vault earns 7% of the base value, so Debt clears after Horizon × rate/base. Observed: a 1-month Advance shows an Unlock Estimate ~24–25 min (A's 497 Gemas opened 14:50, estimate 15:14); 3 months shows 74 min; ETH 1 month 21 min (1 simETH = 2.06 ETH on the Hoodi SimLST). At this pace, on Oct 12 (rate ≈ 11.6) 1 month takes ~2 h and 12 months ~23 h, while every amount says "1 month = 10 min". Program/contract fix (needs the founder's OK): re-base or compound the pools (e.g. an admin re-base of `base_rate`/`base_ts`), or accrue on the current value.
3. **P2: the Queue doesn't pair Players who enter close together.** Repro A: two browsers press Play now at the same moment (Block Puzzle 500, 14:55:22): two Matches (`3581733052314`, `3581733052962`), each waiting for an opponent who is already waiting in the other. Repro B: Hold'em 500, A opens `3581735340102`, B presses Play now 10 s later and opens `3581735359890`. A 6 s gap did pair once (`3581734608480`), so this is timing-dependent. Cause: candidates come from the cached list route (`app/src/server/gpa.ts:72–73`, 4 s fresh, served up to 120 s stale), and `enterQueue` (`app/src/lib/chain/match-flow.ts:95`) opens a new Match when it sees none, with no second look for a concurrent opener. Two lonely Matches only resolve when a third Player arrives or each Player cancels.
4. **P2: a stale raw error stays under a settled result.** Seen as "base tx failed 2qwowjqBt…: {"InstructionError":[0,{"Custom":0}]}" on the backed Player's win (`3581736037312`), the opponent's loss, and the Challenge winner (`4vLn12jYx9…H1ERNZaX`), and as "Your opponent is still playing." under C's settled backed loss. Cause: when two clients (and the keeper) settle at once, each sends `open_holding` for the same missing payout Holding (`app/src/games/block-puzzle/chain.ts:540–560`); the loser fails "Allocate: account … already in use". `MatchView` sets `error` while awaiting (`app/src/components/match/MatchView.tsx:121–124`, `:388–389`) and renders it on the result (`:256`) without clearing it when the phase becomes `result`.
6. **P3: duplicate transactions on every Match (fees and noise).** Block Puzzle settle losers fail `Custom 6015` (`3BuEFrBM7T…P3i6xgGT`, `46M98rjH…`, `xG4BTFsF…`, `3JApALEA…`, `PiwnKTuX…`), Hold'em finalize losers `Custom 6018` (`3KRUuUZ99v…BQF4849A` from the keeper, `62wLucRY…`, `JdfWwMvf…`, `5WyKzoLW…`, `2aAaTZx2…`), and each Hold'em table gets two failed `create_match` ("already in use") 36 s and 72 s after it was created (`5mcqF7wB…`, `5i9vQ6Mi…`; `2BnuS73m…`, `dErm9ynJiR…hTKFHS2d`), from the step-in path in `app/src/games/holdem/useHoldemMatch.ts:157–170`. 7. **P3: Challenge Matches use Queue copy.** On `3581739773833` the ready screen says "No opponent yet: play now and you will be paired with the next Player." (`MatchView.tsx:350`) and the waiting screen "The next Player to join plays the same Seed…" (`MatchView.tsx:306`). ## Known limitations

- Hold'em table setup took 123–131 s (create, delegate, permissions, VRF, deal). The result screen appeared about 2 min after the on-chain `finalize` (15:11:10 → 15:13:01; 16:15:41 → 16:17:37).
- Reloading during a Block Puzzle run closes the run with the moves that had landed (48 on screen before the reload, 44 settled). By design.
- List reads are cached (`/api/chain/accounts`, 4 s fresh, up to 120 s stale): a new Position appeared in the Wallet ~25 s after its tx, and an accepted Offer card briefly still showed "Accept".
- The Queue page correctly refuses an entry the Account cannot cover ("You do not have enough Gemas for this entry"), but only after Play now; the game page entry picker does not warn first (B with 480 Gemas at 500).
- Unlock returns the Principal minus the reserve for Gemas of that Source still outstanding (A: 0.98944 of 1 simETH).
- TEE transactions (claim_timeout, act, close_match) are private: the page lists them, the explorer cannot.
- The Next.js dev indicator ("N", "12 Issues" during the Hold'em Match) sits over the corner Guide's bust in dev only. On the main routes the console showed only one Next/Image sizing warning (`him-explain.webp`).
- Full-page screenshots draw fixed bars (bottom nav, sidebar) mid-page. Not a layout bug.
- HyperEVM: not deployed (no HYPE), not tested.
- `qa10a`, `qa10b`, `qa10c` and their Matches and Positions stay on devnet / Hoodi. `qa10a` has an ETH Position #2 now unlocked and a native Position unlocked; `qa10b` has ETH Position #3 and three native Positions with Debt.
