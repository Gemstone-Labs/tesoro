On chain, replay protection is layered: `Endpoint::clear` burns the nonce on Solana, the EVM endpoint tracks nonces, and both handlers additionally apply a message only when `seq` is greater than the last applied one (duplicates and stale messages are consumed as no-ops and emit `applied=false`). ## Findings and pitfalls (read before building `tesoro_core`)

1. **Executor native drop to Solana is capped at 0 on Hoodi and HyperEVM.** `dstConfig(40168).nativeCap == 0` on both executors (Sepolia's is 1e7 lamports). Sending an `lzReceive` option with a non-zero `value` reverts with `NativeAmountExceedsCap`. So nobody can fund rent for accounts created inside `lz_receive`. The OApp therefore never creates accounts in `lz_receive`: Position records are created beforehand with the permissionless `init_position(eid, position_id)` (the user or keeper pays once on Solana before the first message for that Position). If it is missing, `lz_receive` fails and the message stays retryable (`lz_receive` is permissionless) until the account exists.
2. **The executor sends Solana v1 transactions.** `getTransaction` needs `maxSupportedTransactionVersion: 1`; older clients and explorers that pass 0 see an error. Keeper code must set it.
3. **Account list for `lz_receive_types_v2`** (order is a contract with the `LzReceive` struct): payer, store, peer(src_eid), position(src_eid, message position id), system program, then the `Endpoint::clear` accounts from `get_accounts_for_clear`. Position and peer PDAs are derived from `src_eid` and the message body, so the message must carry the Position id at a fixed offset. `tesoro_core` accounts (Match, Debt, Advance) must be derivable the same way. No ALT was needed at this size (`alt` is optional in `init_store`; pass the program id for None).
4. **The OApp address is the Store PDA, not the program id.** EVM `setPeer` takes the PDA as bytes32.
5. **Public devnet RPC is the bottleneck.** `api.devnet.solana.com` returns 429 constantly with several agents sharing one IP; `solana program deploy` aborts on the first 429 and restarts from zero. `spikes/lz_oapp/scripts/upload.ts` is a paced, resumable buffer writer (rotates across RPCs); use it and then `solana program deploy --buffer` or `upgrade`. A program upgrade that grows the binary needs `solana program extend` first. Budget 15 to 25 minutes per program upload on a congested day; get a keyed RPC (Helius) into `~/.env` for the real deploys.
6. **Toolchain:** `cargo build-sbf` (platform-tools Cargo 1.84) cannot parse edition-2024 crates; the lockfile is pinned via `cargo update -p blake3 --precise 1.5.5` (and `rust-version = "1.84"` for fallback resolution). The program is 486 KB (lto, opt-level 3); `opt-level=z` gives 405 KB if upload time matters. This workspace is separate from `programs/` because of the `oapp-latest` git dependency (`LayerZero-v2` rev `c09287a`, Anchor 0.31.x).
7. **EVM `OApp` from `@layerzerolabs/oapp-evm` 0.4.1 + protocol-v2** is vendored into `contracts/lib/@layerzerolabs` and `@openzeppelin` (5.6.1, trimmed) with `contracts/remappings.txt`; `forge build` and `forge test` still pass.
8. **Options for EVM to Solana**: type-3 executor `lzReceive` option, gas field = compute units (200,000 used; actual use 56,749), value 0. Solana to EVM: enforced options stored in the peer config (150,000 gas; actual 102,395).
9. Fees are small: about 0.0001 ETH per Hoodi send, 0.0003 SOL per Solana send, about 0.0074 HYPE per HyperEVM send (fork quote).

## Integration plan for `tesoro_core` and `PositionVault`

- **Solana:** keep the OApp as its own program (Anchor 0.31.x pin, `oapp-latest` dependency) and CPI from it into `tesoro_core`, or fold `lz_receive` into `tesoro_core` with the same account order. Recommended: keep `lz_oapp` separate so `tesoro_core` stays on its own toolchain; `lz_receive` CPIs `tesoro_core::apply_position_message(msg)` with the Position/Debt PDAs derived from `(src_eid, positionId)`. Sends (`Unlock`, `PayYield`) are CPIs from `tesoro_core` (PDA signer) into `lz_oapp::send`, replacing the spike's admin signer.
- **Position records:** the `init_position` requirement (finding 1) becomes a step in the wallet flow: the app creates the Solana-side Position record in the same session as the EVM lock (or the keeper does, funded from the faucet wallet) before `PositionVault` sends `PositionLocked`. Failed `lz_receive`s are retried by the keeper.
- **EVM:** `PositionVault` inherits the `OApp` pattern of `TesoroSpikeOApp`: `lock()` sends `PositionLocked`, the keeper's `reportYield()` sends `YieldAccrued`; `_lzReceive` handles `Unlock` (release Principal once, keyed by `seq`) and `PayYield` (bounded by reported accrued yield). Reuse `lastIn`/`lastOutSeq` idempotency and the `sourceChain == endpoint.eid()` check.
- **Wire format:** freeze the 61-byte layout above; extend by appending fields and bumping the length check, never by reordering.
- **Fees:** the EVM caller pays the quote in the native token (0.0001 ETH class); Solana-side sends are paid by the keeper. Show cross-chain progress in the app from LayerZero Scan (`/v1/messages/tx/<hash>`: INFLIGHT, CONFIRMING, DELIVERED).
- **Latency to design for:** 2 to 6 minutes per hop on Hoodi. Wallet copy and the demo script should not promise instant unlock.
