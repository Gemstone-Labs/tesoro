## Point 1 — Hidden deck: PASS

Design (all in `programs/holdem/src/lib.rs`):

1. `create_match` (base) creates Match, Deck, Hole0, Hole1 PDAs; `delegate_match` delegates all four to the TEE validator.
2. `init_permissions` (TEE) creates EphemeralPermissions: Deck = **private with zero members**, each Hole = private with its Player only, Match = private with both Players.
3. `contribute_entropy` (TEE): each Player sends a 32-byte secret; the Deck folds it in with `hashv`. Only ever executed in the TEE.
4. `request_vrf` (TEE) calls the VRF program; the oracle's callback `vrf_callback_shuffle` writes the output **only into the private Deck**.
5. `deal` (TEE) seed = `H(entropy || vrf)`, Fisher-Yates over 52 cards with per-index hashes, cards to Hole accounts.

Why it is unreadable and unpredictable:
- The VRF output never lands in a public account or base-layer tx. Request, callback and consumption all happen inside the TEE, and it is stored in an account nobody can read (empty member list).
- Even a leak of the VRF output would not be enough: the seed also needs both Players' secrets. Neither the operator of one seat nor a VRF observer can rebuild the deck alone.
- Evidence: every actor (player0, player1, an authenticated outsider) gets `null` for the Deck over the TEE RPC; the base-layer copy of the Deck stays all-zero (entropy, vrf, cards) the whole hand because the delegated state is only committed after `close_hand` wipes it. An outsider fetching the TEE txs of the hand (including `contribute_entropy`, which carries the secret in instruction data) gets a redacted transaction: empty message, no logs, no balances.
- Trap check: no shuffle input is derived from a public value. The base-layer transaction list contains no randomness.

Trust assumption (state honestly): the TEE operator/Intel TDX attestation. The Program itself can read the Deck. A member-less private permission means "no external reader", not "encrypted".

## Point 4 — Clock (turn timeouts and no-shows): finding, not tested on-chain

Not proven by this spike; the crank API on the TEE was **not** exercised. MagicBlock ER cranks (`ScheduleTask` via the Magic program: task id, interval ms, iterations, instructions) are documented for ephemeral rollups, but the docs page does not state TEE availability, minimum interval, iteration cap or who pays. Treat as unverified.

Recommendation, which does not depend on cranks working:
1. Store `turn_deadline_ts` (from the Clock sysvar inside the rollup) in the Match on every action.
2. Enforcement is **lazy and permissionless**: an instruction `claim_timeout` that any Player (or keeper) can call once `now > turn_deadline`, forfeiting or folding the stalled seat. No liveness needed from anyone but the honest Player, who is motivated to call it.
3. The keeper (`keeper/`) is a convenience that calls `claim_timeout` for stalled Matches so Players do not have to; a crank may replace it once a TEE test passes.
4. A no-show at deal time (a Player never contributes entropy) is the same mechanism: a deadline on the entropy phase, after which the Match is cancelled and both Chips refunded from the base-layer Pot.
5. Follow-up test (about an hour): `ScheduleTask` in the TEE that calls `claim_timeout`.

## Pitfalls

- `pnpm build:programs` only; plain `anchor build` fails (Cargo 1.84 vs edition 2024 crates).
- Send delegation to the base layer, everything else to the TEE, with `skipPreflight: true`. TEE txs need a token from `getAuthToken` (sign the challenge with each Player's key), one connection per Player.
- Ephemeral permission rent is paid by the delegated PDA on the rollup, so `create_match` prefunds each PDA with `ephemeral_accounts::rent(EphemeralPermission::size_of(n))`. Permissions are created by CPI signed by the PDA seeds.
- Account reads that are not permitted return `null`, indistinguishable from "does not exist"; do not use that for error handling.
- Delegate with the TEE validator pubkey explicitly, or the account goes to the default validator.
- Delegation needs a raised compute limit (600k used for four accounts).
- Close hidden accounts (`close_hand`) before undelegating: whatever is in state at commit becomes public on the base layer. Wipe first.
- Devnet: `api.devnet.solana.com` returned 429 for over an hour (shared IP); a 538 KB program deploy failed repeatedly there. Use `https://rpc.magicblock.app/devnet` with `--with-compute-unit-price` and `--use-rpc`. Failed deploys leave buffer accounts holding about 2.5 SOL each; close them.
- The first checks of the flow (create, delegate) take several seconds to propagate; the script polls owner changes.

## Recommended real Hold'em design

- One Match PDA plus a Deck and two Hole accounts per hand, delegated to the TEE on Match start; Chips live in the Match in-rollup (Pot stays on base layer via tesoro_core, only the result crosses back).
- Deck seed = `H(both Players' secrets || VRF)` exactly as here. Players submit their secrets from the client inside the TEE session; add a commit-reveal of the secret hash before the VRF request if a Player must not be able to grind after seeing the other's contribution (they cannot read it, so grinding is already blocked; the hash commit is an extra).
- Reveal community cards by writing them to the Match (public to both Players) and only at showdown to the Hole accounts; wipe Deck at hand end.
- Settlement: `settle` records the result and commits + undelegates the Match; tesoro_core accepts the Pot release only from an account owned by the registered Game program with `settled=true`.
- Clock as in point 4.
- Cost: no game server, and the TEE operator is the trust root. Disclose that in the UI and in the ADR.
